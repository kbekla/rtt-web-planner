# RT&T Scout worldwide route research foundation

Scout is a private, regional research system. A route file is an observation, not a trail record: its complete source geometry and bytes remain private, while versioned derived segments and candidate corridors are separate records. Candidate identity, source observation identity, and any matched canonical `rtt_id` are kept separate. Nothing in this pipeline writes to the canonical master or public trail artefact.

## Geographic and source model

`ScoutGeoStore` stores a versioned source registry, source-file history, route observations, network snapshots, jurisdiction versions, derived segments, candidates, evidence, and review items in a private SQLite database. Spatial features have RTree indexes and bounded viewport queries. Raw file bytes are SHA-256 addressed in a distinct private directory. Both paths must be explicitly configured outside public repository roots; the store refuses symlink roots and the importer refuses symlink inputs. Use one regional processing batch at a time rather than loading worldwide source graphs into memory. Route processing has explicit cell, vertex, and edge budgets and requires a pinned network snapshot.

Every registered source describes its stable ID, name/type/organisation, location, expected formats, adapter version, country/region/jurisdiction coverage, licence and version, attribution, private processing/redistribution/derived-public-use permissions, evidence roles, update mechanism, and rate limits. These permissions are independent: public availability does not imply redistribution. Boundary and routing-network snapshots require a registered source with the corresponding role, version, checksum and licence. Source registry revisions and jurisdiction boundary versions are retained for audit.

Jurisdictions use stable IDs, ISO alpha-2 country codes, optional first- and second-level administrative codes, original language, effective dates, and versioned Polygon/MultiPolygon boundaries. A physical observation can cross multiple jurisdictions without splitting its physical identity. Segment-level jurisdiction annotations scope legal/access evidence separately; the assignment layer does not interpret local law. Boundary attribution is currently deterministic route sampling against explicitly supplied boundaries. It is a review/indexing aid, not a legal boundary determination; narrow or complex boundary crossings require exact clipping and authoritative review before operational use.

## Explicit local route ingestion

The importer accepts one caller-selected regular file at a time and requires an already registered source that permits private processing. It does not scan Downloads or any other directory, follow symlinks, retrieve URLs, or infer source permissions. Current parsers handle GPX 1.1, KML LineString/MultiGeometry and GeoJSON LineString/MultiLineString features. KMZ and ZIP containers are intentionally not unpacked yet. XML parsing rejects DTDs and entity expansion. Import is checksum-aware and idempotent for `(source, relative name, checksum, parser version)`; a changed file creates a new source-file version while preserving the previous raw object and its observations. Multipart geometry stays multipart, missing names/IDs remain valid, language and original properties are retained, and source coordinates are not snapped, simplified, or rewritten.

The importer has no recursive manifest scanner or operational CLI yet. Before a real collection is loaded, the owner must identify the selected file set and register each source with its private-processing permission, licence/terms, attribution, source identity and permitted use. For TET, ABR, community, or user route material, the original remains restricted private discovery material unless a separate licence grants more. Route use never proves motorcycle access or public redistribution rights.

## Deterministic segmentation and candidate extraction

Processing requires a checksum-pinned, registered routing-network snapshot for the observation's region. For each original route vertex, the current first implementation finds nearby network-edge segments within a configurable snap radius. It uses network class, surface, tracktype and explicitly qualified physical-existence evidence:

| Segment class | Current deterministic interpretation |
|---|---|
| `ROAD` | Recognised ordinary road class or explicit paved network edge. |
| `UNSEALED_ROAD` | Recognised public/road-like class with unsealed surface or lower track grades. It is not automatically a trail candidate. |
| `PROBABLE_OFFROAD` | A track/path-like edge with sufficiently trail-like surface/tracktype. This is physical character only. |
| `OFFROAD_CONFIRMED` | Trail-like network edge plus separately qualified, source-role-authorized physical existence evidence. |
| `UNKNOWN` | No match, unknown tags, sparse transition, or competing nearby network classes. |

Source filenames, GPX names, rider labels, and route popularity are not classification signals. A close parallel edge with competing classes becomes `UNKNOWN`; proximity alone does not choose the identity. Adjacent short class transitions use midpoint boundaries. A long gap over the configured boundary limit is retained as `UNKNOWN`, avoiding invented transitions. A brief mapped road crossing can remain within one candidate section under a configurable short-crossing rule. Disconnected source parts are never joined. These rules operate on route vertices and are deliberately conservative; they are not a production-grade probabilistic map matcher. Sparse sampling, off-network geometry, complex junctions, and closely spaced roads require review or a better region-specific matcher before trusted candidate geometry is produced.

The full source geometry is always retained. Ordinary `ROAD` runs are not emitted as candidate trails. `UNSEALED_ROAD` is distinct and reviewable but is not automatically promoted to a trail candidate. Only `PROBABLE_OFFROAD` and qualified `OFFROAD_CONFIRMED` runs produce derived candidate objects; unknown/unsealed cases can create explicit review items. Each derived feature records its source observation, component and vertex range, pipeline version, geometry, jurisdiction relations and classification evidence. Physical existence, motorcycle access, and routability remain independent, with access/routability initially `unknown`.

Candidate geometry is compared against an explicitly supplied immutable canonical master through the read-only matcher. The integration requires exactly 14,315 unique `rtt_id` features for this master generation, computes and records a checksum, rejects symlinks, and exposes no write API. Exact match, likely match, partial overlap, possible parallel, ambiguity and new candidate remain distinct states. A match does not merge either geometry. Corridor hypotheses group independent observations only when they share stable, version-pinned network edge identities; observations, original geometries, dates and evidence remain recoverable. This first corridor method will miss equivalent lines from incompatible network IDs rather than risk proximity-only merging.

## Private review map and scale boundary

`npm run scout:review:synthetic` starts a development-only MapLibre reviewer on loopback. It uses the existing RT&T/OSM/OpenMapTiles Monaco basemap and synthetic data only. The server does not mount the geostore or raw-file directory. Its allowlisted endpoints and tile/style assets are read-only; the repository's public server and PMTiles build are unchanged. The fixture map separates original source route, physical-character segments, and canonical comparison; filters classification, match, country/region, physical existence, access, routability, review state and source. Segment colour represents physical character while line pattern represents canonical-match relationship. Selection shows candidate/status properties. Viewport segment queries are bbox filtered, including antimeridian bounds.

For worldwide operation, regional ingestion and indexed records are the primary processing boundary. SQLite plus RTree is an appropriate single-host foundation and supports bounded viewport reads; it is not yet benchmarked for millions of global edges or multi-user concurrency. A production reviewer should expose only generalized/vector-tile or viewport-query layers with pagination and regional scoping, never raw restricted source bytes. PMTiles is suitable for immutable basemap or explicitly approved display snapshots, not as the live candidate/evidence database. A future storage migration can preserve the stable source, observation, segment, candidate and jurisdiction IDs.

Before the first real GPX collection, select the exact files or manifest, establish rights to private processing, register source and attribution/retention terms, choose a bounded private storage location, and supply a matching regional network snapshot with a verified licence/checksum. Review the resulting segmentation against known routes before considering broader batches.

## Verification in this worktree

Synthetic tests cover GPX/KML/GeoJSON parsing, unchanged source geometry, file checksums and versioning, parser/security failures, road/trail transitions, parallel-edge ambiguity, cross-border evidence scopes, read-only canonical matching, candidate persistence, and private MapLibre filtering/inspection. The review browser test uses a synthetic Monaco map fixture. These checks validate the software boundaries and fixtures; they do not constitute a legal determination or validate a real source collection.
