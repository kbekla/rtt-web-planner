# RT&T Scout — Milestone 1 foundation

Scout is a private trail discovery and investigation queue. It collects and preserves observations, matches candidates against the RT&T master when supplied, records evidence and open questions, and prepares review items. It does not build maps, decide legal access from route popularity, import to the canonical master, or publish data. The existing deterministic trail factory remains the sole validation and promotion authority.

## Data and decisions

Each candidate has a stable hash-derived `candidate_id`, version and timestamps, unchanged source observations, geometry and its hash, master-match result, qualified evidence references, three independent states, confidence/review notes, corridor relationships, issues, and lifecycle/review state. `schema/scout-candidate.schema.json` describes the persisted record. Raw source geometry is copied without snapping or simplification. Any future transform must preserve the original and name the transform and version.

The states are deliberately independent:

| Question | Values | Meaning |
|---|---|---|
| Physical existence | `unknown`, `probable`, `confirmed`, `disproved` | Evidence that a physical lane/path/track exists. |
| Motorcycle access | `unknown`, `probable`, `confirmed`, `prohibited` | Evidence about motorcycle-specific access. Route use or a source label never supplies legal evidence by itself. |
| Routability | `unknown`, `yes`, `no` | Whether the routing engine can enter, traverse and exit the geometry. |

Source evidence metadata and route hints are kept as descriptive observation data. They do not affect state until a separate evidence-review step marks an evidence record `qualified`. Contradictory qualified evidence is retained and marked `contradictory`; it queues review. Unknown access is never changed to permission by matching, routability, names, AI, or community-route use.

## Sources, matching and review

Collectors implement `collect(cursor)` and return observations plus a cursor/check time. `FakeAdapter` is the only included adapter. A source observation can have or omit geometry, source ID, name, provenance, hints and evidence. Hints are discovery-only. `SourceScheduler` enforces a minimum interval, persists cursors/check times, applies bounded exponential retry times and holds a source in AMBER after its retry budget. Source failures are recorded per adapter and do not stop another adapter's queue.

Matching is deterministic and read-only. Byte-equivalent geometry is `EXACT_EXISTING`. Other geometries receive line-distance and sampled overlap scores. High overlap and close shape can be `LIKELY_EXISTING`; partial shared length is `PARTIAL_OVERLAP`; nearby without overlap is `POSSIBLE_PARALLEL`; competing matches are `AMBIGUOUS`; no close match is `NEW_CANDIDATE`. Proximity alone never establishes identity. Thresholds are loaded from `config/scout.yaml`; uncertain outcomes stay reviewable. The matching API accepts master features but this worker does not load or change a canonical master, so it records `UNMATCHED` until a future controlled integration supplies that master.

The original worker's geometry-based corridor grouping is advisory only. The worldwide geostore foundation groups independent observations only when they share stable, version-pinned network-edge IDs; it never combines candidate records. See [SCOUT-WORLDWIDE.md](SCOUT-WORLDWIDE.md) for current route import, segmentation, jurisdiction, review-map, and scaling details. Review items persist a reason, relevant match/evidence/state fields and recommended action. A no-geometry hint is retained and queued rather than dropped.

## Worker, state and control

`scripts/scout/core.mjs` provides an atomic JSON queue under `$FACTORY_DIR/scout/`, deterministic job IDs for duplicate prevention, pending/running/held/done states, bounded exponential retry delay, and recovery of interrupted running jobs. Corrupt persisted queue data creates a durable RED sentinel that prevents restart loops from processing further work. Candidate and review files, source cursors, worker heartbeat and last activity are in the same private root. `scoutctl` supports status, a read-only live `host` snapshot, list, show and explicit synthetic fixture enqueue. `worker.mjs --once` processes queued local observations only. Source scheduling is an explicit API boundary; no scheduler is activated. There is no crawler, import command, `factoryctl` authority, or active systemd unit.

The service file is a dormant deployment template with low CPU/IO weights and filesystem protections. Its `@SCOUT_DIR@` and `@FACTORY_DIR@` values must be supplied by a later reviewed installer; it does not point at the live runner and is not installed or enabled. Scout cannot approve factory jobs, clear factory RED, deploy code, promote a master, or publish trails. A future Control Centre can read the private status and queue JSON without gaining these authorities.

## AI boundary

The `consultAI(provider, request)` interface is optional and disabled by default. It applies a timeout, validates a small advisory response, and bounds its fields. Disabled, unavailable, timed-out, provider-error, malformed or quota-failed calls leave deterministic processing available. AI output cannot set the three evidence states or change a match. `consultAIAndRecord` stores bounded private consultation records with provider/model, reason, candidate/job and evidence references, response, action, uncertainty and usage when supplied. Fake providers support tests. Production escalation policy and credentials are future work. The future strong-model/Astra escalation should be limited to policy-triggered ambiguity or integrity cases. Cross-model consultation was used once during Milestone 1 to review geometry identity risk; its recommendation was adapted into conservative length-weighted matching and identity corroboration requirements.

## Host cooperation and thermal policy

The host classifier consumes a provider-neutral snapshot compatible with `scripts/lib/telemetry.mjs`: factory state, Planetiler, other heavy lease, local AI, RAM/swap/load, CPU/iGPU/dGPU/NVMe temperatures, disk/scratch, and throttle/clock data as available. `scripts/scout/resources.mjs` reuses current telemetry and adds read-only systemd, process, Ollama, lease-file and disk probes. A17 validation on 2026-10-04 found CPU sensor `/sys/class/hwmon/hwmon5/temp1_input` (`k10temp`, Tctl), NVMe `/sys/class/hwmon/hwmon3/temp1_input`, and AMD iGPU sysfs telemetry (temperature, utilization, used/total VRAM). A sample read CPU 54.3°C, NVMe 32.9°C, iGPU 52°C at 15% busy with 483 MB VRAM used. `/proc/meminfo` provides MemAvailable (about 8.3–8.5 GiB available of 14.5 GiB total), SwapTotal/SwapFree (4 GiB total, about 1 MiB used); load comes from `/proc/loadavg`; disk free/total comes from `statfs` on the configured factory root (about 435/502 GB free in the validation sample). These fields remain nullable when an OS interface is absent.

The A17 exposes an NVIDIA DRM device, but at validation the driver CLI reported that it could not communicate with the driver, so temperature, utilization and clocks were unknown. The sampler attempts NVIDIA queries only when runtime PM already reports `active`, uses bounded commands, and returns null on driver/query failure. If available, it records temperature, utilization, VRAM, core/memory clocks and throttle reasons. It never queries `power.draw`; the known GTX 1650 bogus ~170 W / SW Power Cap value is not a thermal input. The live probe found the factory idle, no Planetiler process, no active Ollama model/service and no other recognized heavy process. Factory state combines systemd service state, the factory running queue and read-only process cmdlines; Ollama state combines its service/server process, `ollama ps` and known local inference process names. Existing successful-build telemetry records both GPU sensors: the successful UK build peaked at CPU 76°C, NVMe 54.9°C, iGPU 55°C and dGPU 51°C; Monaco peaked at 51.4°C, 32.9°C, 40°C and 41°C respectively. The UK run also reached 13.7 load1 and 10.2 GB scratch, so load is a configurable contention signal, not a standalone thermal trigger.

`scripts/lib/resource-admission.mjs` is the development implementation of the shared admission protocol. Both factory-priority work and Scout/local-AI background work use one machine-wide `state/resource-admission.json` plus a short `flock` gate. Factory publishes its intent under that gate before requesting admission; new background leases are refused, active background work observes the intent and checkpoints/yields, then factory takes the lease. Intent, lease and release are nonce-checked atomic transitions. The status record carries owner, priority, phase, PID/process-start identity, boot ID and workload process group. Previous-boot leases are reclaimable; same-boot recovery requires proof the owner and workload group have stopped. Unknown/malformed records fail closed. Process-group existence errors or possible PGID reuse conservatively block admission.

The launch lifecycle is `reserved` → `launching` → `running` → release. Production integration must start a blocked wrapper, bind its workload PGID while it is still blocked, and only then authorize it to execute; a crash with unresolved `launching` state remains blocked. All build descendants must stay in the tracked process group (a dedicated cgroup is preferred if tools can daemonize or call `setsid`). `ScoutHeavyWorkCoordinator` continues to checkpoint at bounded chunks, unload optional local AI, and release background admission on yield. This protocol has synthetic priority, concurrency, crash and reboot tests, but neither the development factory worker nor a deployed Scout worker currently uses it. `factory_coordination_verified` therefore remains false and heavy Scout work fails closed with `BLOCKED_FACTORY_COORDINATION_UNVERIFIED`, even on an idle host. Do not enable the flag or deploy this protocol until both workers use the launch handshake and yield behavior. Systemd resource controls remain low priority in the dormant unit. Thermal policy never consumes NVIDIA power draw.

Initial configurable hold points in `config/scout.yaml` are WARM CPU 85°C / NVMe 65°C, HOT CPU 90°C / NVMe 72°C / GPU 85°C, and CRITICAL CPU 98°C / NVMe 80°C. The observed successful UK build peaked 9°C below WARM CPU and 10.1°C below WARM NVMe, so the initial WARM points retain margin over the measured build. These remain conservative provisional values, not hardware vendor limits or a substitute for more build samples. WARM immediately prevents new heavy work. HOT requires three readings spanning at least 20 seconds; CRITICAL immediately enters RED. Load and swap contention also require three readings spanning 20 seconds. The governor uses a 5°C recovery margin and six cool samples at ten-second intervals. HOT pauses heavy work; CRITICAL enters RED/thermal hold. It never shuts down the OS. The known GTX 1650 bug reports about 170W despite a 50–60W configured limit and SW Power Cap; that power field is ignored. Temperature, utilisation, clocks and real throttle indicators are the relevant corroborating signals.

## Notifications and privacy

`NotificationCenter` writes durable notification/digest state, supports EMAIL and SMS provider slots, dedupe keys, cooldown, severity escalation and one recovery event. Delivery exceptions are recorded per channel and swallowed so Scout continues. INFO can be batched; AMBER needs review or indicates degraded safe operation; RED means integrity or safety hold. Test providers require no credentials. Message adapters should send only brief summaries and private review IDs. `scripts/scout/zoho-smtp.mjs` supplies an EMAIL provider for Zoho EU using SMTP STARTTLS with certificate verification; it loads its app password only from `/home/karl/.config/rtt-scout/credentials/zoho-smtp-password`, requires a regular owner-only non-symlink file, and returns sanitized errors. It performs no retries. Creating the provider validates the credential file, while `verifyConnection()` checks STARTTLS and authentication without sending a message. This adapter is available to a caller through the existing provider slot; it does not activate a Scout service or schedule delivery. The SMS slot remains provider-neutral and unconfigured until Karl selects a provider.

All evidence, provenance, candidates, cursors and review records live under `$FACTORY_DIR/scout/`, outside web-served repository paths. Public trail projection stays governed by the Phase 3c whitelist (`rtt_id`, `name`, `kind`, `access` plus geometry). Scout does not add fields to that contract or write to the 14,315-feature canonical master. Repository fixtures use synthetic identities only.

## Milestone 1 scope and limits

Milestone 1 supplies data contracts, deterministic normalization/matching/clustering, review persistence, replaceable AI and notification interfaces, queue/worker foundations, a resource-state abstraction, thermal hysteresis and a dormant service boundary. It contains no live internet source, real trail data, production credentials, canonical import, publication, automatic deployment, or shutdown policy. The system is safe to leave dormant while the pinned live map factory continues operating because no unit is activated and no shared factory or canonical paths are modified.

## M2 execution boundaries

M2A has a read-only `scoutctl host` probe and `scoutctl status` view for live sensors, detected workloads, lease owner, coordination verification, blocked reason, thermal state, AI state, notification counts, regression health and last successful activity. It uses fail-closed factory/Ollama/lease detection, a sustained-signal governor, and cooperative checkpoint/yield/resume with synthetic tests. Actual A17 sensor formats have been checked read-only. The factory worker is not yet integrated with shared admission, so live factory-priority contention remains unverified; heavy Scout work stays blocked. Live telemetry is observational only. Do not induce load, stop Ollama, restart services, or reboot while the map factory is active; those checks require a safe A17 window. Simulated crash/reboot recovery tests do not replace a real reboot exercise.

Regression-stall diagnosis: `npm run test:unit` completed 46/46 in about 17 seconds, `npm run test:scout` completed 93/93 in about 8 seconds, and the 62-test foundation file completed in about 5 seconds when local subprocess permissions were available. The apparent stall/failures reproduce under the restricted execution sandbox at shared-admission tests 51–54: `SharedResourceAdmission.transition()` synchronously starts `flock` and a Node helper, and the concurrency test starts two child Node workers. The sandbox blocks those child processes; bounded 5-second gate timeouts then look like a hang. There is no leaked worker, Ollama probe, socket, or timer when run with normal local process permissions, and the tests exit cleanly. This is an execution-environment restriction; admission remains deliberately fail-closed when its locking helper cannot run. The existing public render suite completed 8 passes and 10 intentional trail-render skips (those require `RTT_TRAILS=1` and the opted-in synthetic trail artifact); the private Scout MapLibre browser test passed separately with synthetic fixtures.

For an unattended systemd service, use `LoadCredential=` or an equivalently protected external secret file. The current Zoho adapter reads only the pinned A17 path above; systemd credential-directory support is not wired yet. Before service activation, Karl must choose whether to keep that protected file available in the service namespace or authorize a reviewed adapter change to read systemd's credential path. Do not place credential values in environment variables, command arguments, Git, logs, status or Control Centre data. One operator-authorized Zoho SMTP test was delivered on 2026-10-04 through `NotificationCenter` to the configured recipient after a separate STARTTLS/authentication-only preflight. The delivery wrote notification status only under `/tmp`; it did not activate routine delivery or Scout. SMS provider and credentials still require Karl's choice.

M2C has an explicit-input read-only bridge in `scripts/scout/canonical-readonly.mjs`. It has no fallback path, rejects symlinks/non-regular files, verifies exactly 14,315 unique `rtt_id` features, checks file stability during read, computes SHA-256, freezes the loaded master and exposes matching only. Its synthetic fixture proves the matching path does not alter supplied bytes. `docs/HANDOFF-PHASE3C.md` establishes the canonical generation path as `~/rtt-map-factory/private/rtt/master/2026-09-25-4b3b29dc8b1c/master.geojson`; the read-only access contract was validated against that file (14,315 unique IDs and SHA-256 `8aec19f60f9c65eb2cc33e227ee1c03a1fd6c20afa05712b8b02dbc015640ebf`). No trail geometry was changed and no write interface exists. The separately named staging file is not treated as authoritative.

M2D must name one approved source and document its endpoint, reuse terms, politeness and provenance. Its adapter may only enqueue discovery observations into private staging. No source is selected or activated here, and no canonical import/promotion path is added.

## Worldwide route-review foundation

The private worldwide route-review slice is documented in [SCOUT-WORLDWIDE.md](SCOUT-WORLDWIDE.md). It adds a versioned source registry, private checksum-aware single-file import for GPX/KML/GeoJSON, jurisdiction and network snapshot records, deterministic road/off-road segmentation, extracted private candidates, read-only matching, and a synthetic-only loopback MapLibre reviewer. It does not read files just because they exist in Downloads, unpack KMZ/ZIP, crawl sources, or activate ingestion. Before selecting any real route material, establish the source's permitted private use, terms and exact file selection.
